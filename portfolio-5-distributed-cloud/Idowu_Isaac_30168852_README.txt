Distributed and cloud database design discussion
This component is an architecture discussion, which the brief explicitly permits. No cloud deployment, replication test, sharding test or failover measurement has been performed.

Proposed topology: application -> managed PostgreSQL primary in zone A -> standby in zone B; asynchronous read replicas serve delayed reporting. A separate MongoDB replica set stores catalogue descriptions. Backups are encrypted and retained separately, with periodic restoration drills. A managed service should provide private connectivity, TLS, roles, monitoring and key management. Real customer data must not enter this sample.

Consistency and availability: route checkout and balance-sensitive reads to the PostgreSQL primary. A synchronous standby can reduce acknowledged-transaction loss but adds commit latency and may block writes when required standby acknowledgements are unavailable. Asynchronous replicas improve read availability with possible stale reads and data loss during promotion. During network partition, protect the single-writer invariant with fencing and quorum-managed failover rather than permit both primaries to accept orders. CAP is a partition-time tradeoff, not a permanent label meaning a database always sacrifices consistency.

MongoDB replica sets can use majority write concern and majority read concern where required. Causal sessions and explicit read preference matter for read-your-writes. Catalogue browse can tolerate staleness; purchase stock cannot. A replica is not a backup: deletes and corruption may propagate.

Sharding: 200,000 demo orders do not establish a need. First optimise queries and vertical capacity. If growth later requires horizontal distribution, hash customer_id to co-locate customer/order reads, while recognising global product inventory then crosses shard boundaries. Date partitioning can help retention but is not itself sharding across servers. Celebrity customers, scatter/gather sales reports, rebalancing and multi-shard checkout complicate the design. Reserve stock through an authoritative inventory service and use idempotent saga steps/outbox events; compensations release reservations after payment failure.

Operational targets proposed, not achieved: define RPO/RTO with business owners; measure replication lag, lock waits, deadlocks and backup age; test recovery and failover in staging. Do not claim zero data loss or a recovery time without tests. Managed service charges, regional availability and student account limits must be checked before provisioning anything.
